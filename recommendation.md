# Recommendations for Production Deployment

To transition this multi-agent web crawler from a single-machine academic prototype to a production-grade distributed system, the most impactful change is replacing SQLite with a distributed message queue (e.g., Redis Streams or Apache Kafka) for the crawl frontier and a dedicated search engine (e.g., Elasticsearch or Meilisearch) for full-text indexing. The current SQLite `crawl_queue` table works well for single-machine BFS, but a distributed queue enables horizontal scaling of crawl workers across multiple nodes, each pulling URLs from a shared frontier without coordination overhead. For deduplication at scale, a Redis HyperLogLog or Bloom filter can replace the current SQL-based URL existence check, reducing memory usage from O(n) to O(1) while accepting a configurable false-positive rate. Politeness must be enforced through robots.txt parsing (using the `robotparser` library) and per-domain rate limiting tracked in a shared store, ensuring that distributed workers collectively respect crawl delays.

For search scaling and read/write isolation, the current architecture's strength — SQLite WAL mode enabling concurrent reads during writes — translates naturally to a producer-consumer pattern where crawl workers write documents to a queue, and a separate indexing service batch-inserts them into Elasticsearch. This decoupling means search queries never compete with write locks, and the search index can be replicated across read-only nodes for horizontal query scaling. The TF-IDF scoring logic should be migrated to Elasticsearch's built-in BM25 ranking (a more robust variant), while the custom title-weighting can be preserved via field boosting. Observability should be enhanced with Prometheus metrics (crawl rate, queue depth, error rates) and OpenTelemetry distributed tracing to diagnose bottlenecks across the worker fleet. Finally, a circuit-breaker pattern should protect target origins from accidental DDoS when scaling out workers.
